## Task 1 — De-hardcode the outdoor scene for multi-district

D-62: multi-district is architectural from day one even though one district's
content ships. Today a second district would render **zero agents**.

- [ ] `DistrictScene` takes its district id from scene data, not a literal.
      The presence filter becomes "is this agent's venue an outdoor venue in
      *this* district", derived from the registry.
- [ ] `sceneKeyFor()` becomes data-driven: outdoor venues get the district
      scene, indoor venues the parameterised interior scene. No `=== 'district'`
      anywhere.
- [ ] The `farm` string disappears from the client in whichever direction Plan
      `04-` Task 6 ruled — promoted to a real venue, or removed. Three sites:
      `:417`, `:434`, `:449` `[R: R-9]`. Grep for `'farm'` afterwards and
      assert zero hits outside the animal/pen rendering at `:132`/`:392`.
- [ ] **No second district's content ships.** This is capability, not exposure,
      so the measured round stays clean.
- [ ] Test: two districts in a fixture bake each render only their own agents;
      one district behaves exactly as today (a golden-baseline comparison).

## Task 2 — Render the three plot states

- [ ] Read `plot_states.json` (Plan `04-` Task 3) — state → prop composition.
      The mapping is **data**; a fourth state later must not need client code.
- [ ] `vacant` / `claimed` → fenced empty lot.
- [ ] `under_construction` → worksite: `Building_Skeleton`, excavator, site
      fence, stacked materials, worksite ground.
- [ ] `built` → the structure's tier sprite.
- [ ] Tents render on `vacant`/`claimed` plots for agents assigned there, with
      the variant selected deterministically by `spriteSeed`. Same agent, same
      tent, forever. **The pick lives here, not in the bake**: Plan `04-` Task 5
      supplies the pool as bake data, but the bake has no agents and no
      `spriteSeed`, so it cannot select `[R: S-4]`. Use the existing
      `pickFrom(pool, spriteSeed, salt)` from `api/src/utils/agentSeed.js:178`
      — not `scheduleCoverage.js`, which only imports it at `:41` `[R: R-5]`.
- [ ] Test: same seed → same variant; different seeds spread across the pool.
- [ ] ⛔ **O-1 gates this task.** Whether an agent can *be assigned* to a plot
      depends on whether plots carry venue identity — `resolvePresence`
      (`api/src/services/botville/presenceService.js:45-48`) places agents by
      `venueId`, and spec §7.3 says plots are not venues. Under O-1 option (b)
      this task renders a plot's **state**; under (a) it renders a pre-stamped
      venue. Do not build against the wrong one.

Visible construction is the highest legibility-per-token change in the drive:
walking through town and seeing what the city is *currently* building turns an
abstract goal counter into a place an agent can stand next to.

## Task 3 — Generated doors for built homes

This is what finally makes houses **reachable**. Since the district's founding
there has been no house building and no house door on the map, while 85 agents
slept in 13 rooms nightly.

- [ ] Doors for built structures are generated from the plot's `doorAnchor`,
      not hand-authored furniture entries. Hand-placement is the pattern this
      drive exists to retire. `venues/district/venue.json` carries four doors —
      office, cafe, dorm, library — and no house door, which is the gap this
      task closes. ⛔ **O-1 gates it**: a generated door needs a `targetVenue`,
      and what that resolves to is what O-1 decides.
- [ ] Navigation and pathfinding pick up generated doors — verify
      `navigation.ts` / `Pathfinder.ts` route to a plot-generated door exactly
      as to an authored one.
- [ ] Test: a built plot is navigable from a district spawn; a `vacant` plot is
      not enterable.

## Task 6 — Address book / progressive discovery (frontend)

- [ ] Human-facing city map surfaces plots, owners and states — the "address
      book" idea, on the human side where a browser can afford the payload.
- [ ] **The agent-facing equivalent is not a new tool.** It is `get-city-map`'s
      paged, relevance-ordered payload (Plan `01-` Task 6, D-78). Do not add an
      inspect tool here: L2 is measured at zero calls (M-055 — the reflector
      held 15 tools and made none), and L1 growth costs a re-baseline for a
      surface converting at 0%.

## Planning-mode QA

**Blast radius.** Client rendering and the frontend's read surfaces. **No
agents-repo surface moves; this plan never consumes a round.**

**Bracketing checks.** Before: golden-baseline capture
(`scripts/capture-golden-baseline.mjs`) of the current district. After: the
same capture must differ **only** in the ways this plan intends — new plot
states and generated doors. An unexplained pixel diff is a defect, not a
detail.

**Fire-proof.** Point a plot at an undeclared archetype → the render must fail
loudly at build time (I-2: an unresolved name fails the build, never renders as
a missing texture). Give two plots the same door anchor → plot-integrity fails.

**Risk.** Task 1 touches the scene every agent is rendered by. It is a
refactor with a golden-baseline guard, and it should land before plot rendering
so a regression is attributable to one of the two.
